# Storage, encryption and moving the vault

## Data layout

The ASPX application uses `~/App_Data/Vault`, relative to the IIS application's physical directory. It is configured by `VaultDataDirectory` in web.config. Hosted storage must remain in a dedicated subdirectory of App_Data. The server installer grants the application pool Modify on `App_Data/Vault` only, and Read on clients.json/source/configuration. ASP.NET/IIS must continue blocking direct HTTP access to App_Data.

```text
App_Data/
  clients.json                  optional static certificate allowlist (read-only for the pool)
  AgentPackage/                 agent binaries + client installer used for "Add client" packages
  slaps-ca.crl                  last CRL generated by the installer (also imported into LocalMachine\CA)
  Vault/
    audit.jsonl                 metadata/access audit, no passwords
    <device-guid>/
      <rotation-guid>.record.json
      <rotation-guid>.applied.json
    _clients/<device-guid>.json portal-added agents (certificate pin, name, creator)
    _packages/<token>.zip|.json client packages, deleted 24 hours after creation
    _deleted/
      <device-guid>.json        persistent disabled-device marker
      <device-guid>/<archive-guid>/...  recoverable encrypted history
```

The records contain encrypted password payloads. IDs, timestamps, fingerprints, confirmation status, audit and device-deletion metadata are readable JSON. `clients.json` also contains plaintext configuration. This is not whole-file or disk encryption; use Windows/storage controls separately where required.

## Which key protects a password?

Each version uses a fresh random **256-bit AES key** and **AES-GCM** nonce/tag. The agent encrypts password, account and computer information locally. It wraps that AES key with **RSA-OAEP-SHA256** using the public recovery certificate pinned in the agent's `RecoveryCertificateSha256` registry value. Only the wrapped AES key is stored, alongside ciphertext, nonce/tag and authenticated metadata.

The corresponding **recovery certificate's private RSA key** is required to unwrap it. Neither the IIS machineKey, DPAPI nor the old Windows computer identity is part of this encryption. The envelope's `recipientSha256` identifies the complete DER recovery certificate; the history detail view displays it.

| Certificate/key | Purpose | Migration implications |
| --- | --- | --- |
| Recovery certificate + private key | Decrypt stored password generations | Essential; retain each historical recipient certificate with its matching private key. Installed on IIS (LocalMachine\My, CNG) for web reveal; keep the installer's PFX backup offline. |
| SLAPS CA certificate + private key | Issue agent certificates; IIS trusts it for client authentication | Import the CA PFX on the destination (LocalMachine\My), add the CA to Trusted Root and its CRL to the intermediate store (the installer does this when `IssuingCaSha256` matches an existing certificate). Without it, existing agents need new packages. |
| Agent client certificate + private key | Authenticate an agent's HTTPS uploads | Stays on that agent (nonexportable). Copy `_clients` pins and the CA trust to the destination; never copy agent private keys into the website. |
| IIS HTTPS server certificate + private key | Protect HTTPS transport and server identity | Provision a valid trusted certificate for the destination hostname. It does not decrypt vault records. |

For recovery, keep password-protected PFX backups **outside App_Data and the website**. A public CER alone cannot decrypt anything. The installer re-imports the SLAPS CA and recovery keys on the IIS server as **nonexportable** after writing the PFX backup, so the offline backup is the only movable copy: migrate from it with `certutil -f -csp "Microsoft Software Key Storage Provider" -importpfx My <file>.pfx NoExport`. For any other nonexportable key without a backup, it cannot simply be migrated as PFX: preserve its existing supported key/HSM access or plan recovery/re-encryption while that key remains accessible. This implementation does not silently re-encrypt old records during a move.

Expired recovery certificates can still decrypt old records; preserve them. Even renewing a certificate around the same RSA key produces a different certificate fingerprint, so retain the original recipient certificate/key pair referenced by the older envelopes. Changing the agent's recipient pin affects future versions only.

## Moving to another IIS server

1. Back up current storage **before deploying this release**: application startup and new uploads enforce the configured maximum of active versions per device (`App_Data\Vault\settings.json`, default 20; copy this file with the vault so the limit stays the same). If migrating a previous external storage folder, copy its complete contents into the destination `App_Data/Vault`. Include record/confirmation files, audit and any `_deleted` archives/markers.
2. Stop agent services for the migration window, then stop the old IIS application pool to obtain a consistent copy. Do not allow old and new servers to accept different uploads simultaneously.
3. Copy the complete App_Data directory and web.config to the destination directory, preserving `clients.json`, `_clients`, encrypted records and lifecycle markers. Import the SLAPS CA and every required recovery PFX from the offline backups into the destination `LocalMachine\My` (certutil command above, `NoExport`). Then run `Install-SlapsServer.ps1` with the same host name: it detects the existing web.config, reuses the configured CA/recovery certificates, sets bindings, permissions, CA trust, CRL and key access. Do not mirror an empty release App_Data over existing data.
4. If the host name changes, add the new redirect URI to the Entra app registration and update each agent's `ApiUrl` under `HKLM\SOFTWARE\PriCoSoft\SLAPS` (or install a new client package).
5. Verify sign-in, history and reveal of at least one retained version. Check deleted devices remain blocked.
6. Start the destination pool and restart the agents after validation. Preserve the source backup and recovery keys according to your backup policy. No ciphertext rewrite is required when the original recipient certificates/private keys are retained.

The release preserves the v1 encrypted format. An IIS session/cookie may need a new sign-in after moving; this does not change password decryption.

## Retention and deleted devices

At most the **configured number of active encrypted generations** (Settings page, 2–100, default 20, stored in `settings.json`) is retained per device. Lowering the limit trims all active devices immediately. Enforcement runs on application startup (including existing histories) and each upload. It retains the newest candidates plus the most recent known-applied version, replacing the oldest retained candidate if necessary. Superseded records and their applied markers are removed from the active store. Backups are required to recover versions older than those retained; recovery keys alone cannot reconstruct deleted ciphertext.

Administrative portal deletion is recoverable: it writes a persistent tombstone, blocks that device's API access, and moves its encrypted records under `_deleted`. The configured certificate entries remain in read-only clients.json; the tombstone prevents a still-running agent from recreating the device. Administrators can restore the device/archive, which also reenables its configured agent access. There is no automatic permanent deletion of archived devices.

Readers cannot delete or restore. Entra administrators need the `SLAPS.Admin` app role; in certificate mode administrators use `role: "admin"` in clients.json. Management actions require a session CSRF token; deletion also requires typing the exact device name. Keep tombstones during migration, otherwise configured deleted agents could be reenabled unintentionally.
